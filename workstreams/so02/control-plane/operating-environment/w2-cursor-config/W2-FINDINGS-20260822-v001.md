## The four findings that should change a decision

### 1. The guard does not protect the lanes it was written for

`DIRECTLY_REPRODUCED`, and it is the finding that matters most.

Project hooks in this worktree **do not fire**. Four observations agree: a
benign `git status` through the agent's shell tool produced no audit line
although the guard audits every decision including `allow`; `git rebase
--abort` executed and returned 128 instead of being refused; `gh workflow list`
executed and returned data instead of being refused; and a control run first
proved the installed guard denies both of those exact commands when fed the
same payload by hand. Without that control a non-refusal would be ambiguous
between "the hook did not fire" and "the command never matched a rule". With
it, the answer is unambiguous.

The reason is documented and mundane. Cursor loads project hooks from
`<project-root>/.cursor/hooks.json`. The project root in this runtime is
`/workspace` — `core.hooksPath` resolves to
`/home/ubuntu/.cursor/agent-hooks/L3dvcmtzcGFjZQ`, which base64-decodes to
`/workspace`, and the draft build log independently shows the platform
`Cloning into '/workspace'`. This lane's hooks are in `/tmp/oe-w2/.cursor/`, a
git worktree Cursor never reads for project hooks.

The consequence is a genuine conflict between two of L1's own gaps that neither
`APPLY.md` nor the gap analysis notices:

> **G0 says every lane must take its own `git worktree` under `/tmp`. G1 says
> the guard enforces write scope. As written, both cannot hold. The isolation
> G0 requires puts the hooks G1 installs outside the only directory Cursor
> reads them from.**

So the guard will govern a future agent whose project root is a checkout of
this branch. It does not govern a lane working in a worktree — which is every
lane in this group, including this one. Anyone who reads `write-scope.json` and
concludes that `main` is protected client-side is, in the current dispatch
pattern, wrong.

This is not an argument for abandoning worktrees. G0's collision was reproduced
live and cost L1 a recovery; the worktree is the only thing that prevents it.
It is an argument for stating plainly which of the two mechanisms is actually
in force at any moment, and for running the probe rather than assuming.

### 2. `APPLY.md`'s own firing probe would have caused the harm it tests for

`DIRECTLY_REPRODUCED`.

`APPLY.md` says to prove the hooks are live by running `git push origin main`
and watching the guard refuse it. Hooks are not firing here. Had that
instruction been followed, nothing would have intercepted the command and it
would have attempted a push to `main` — a protected branch under this lane's
hard boundaries and under `write-scope.json` itself.

The flaw is structural, not a typo: it tests for a safety net by running the
command the net exists to catch, so the branch of the test where the answer is
"no net" is the branch where the damage happens. The document even says *"Do
not assume the guard is protecting anything until you have seen it refuse
something you actually typed"* — correct instinct, wrong instrument.

The replacement is `.cursor/hooks/probe_hook_firing.py`, which inverts it.
The guard audits `allow` decisions too, so a benign `git status` is a
sufficient positive witness and no refusal has to be provoked. The two
deny-path commands it offers, one per alternation in the `git|gh ` matcher,
are inert: `git rebase --abort` with no rebase running changes nothing, and
`gh workflow list` is read-only. It establishes the control before drawing any
conclusion, and it prints the project-root warning above when it detects it is
running outside `/workspace`. `--arm`, run the printed commands, `--check`.

### 3. `install` is proven to work; `start` is not proven; `terminals` could not be tested

`DIRECTLY_REPRODUCED`.

Draft build `bld-20260822-f72bf7be-cef7-425f-bc38-e86ae43d5e47` — `SUCCEEDED`,
47 seconds, `source AGENT`, `triggerType MANUAL`, the first agent-requested
build in an environment where L1 found eleven of twelve builds `SKIPPED` and
zero agent-requested — settles G3's residual uncertainty, but only partly, and
the parts are worth separating.

**Install runs.** The log carries the script's own output verbatim: `>>> obzio
install: begin`, `Python 3.12.3`, `git version 2.43.0`, the jsonschema install,
`OPERATOR TAXONOMY CHECK: PASS`, `>>> obzio install: complete`, `[INSTALL] Exit
code: 0`. Every line of `.cursor/install.sh` executed in order. L1 observed the
opposite state — a generated wrapper that only echoed *"Started from stale
build … skipping install script"*.

**Start did not run during the build.** The 28,266-byte log contains no `>>>
obzio start: begin`. The only `start:` spans are platform-internal and detached
— `core-dumps`, `desktop-init`, `exec-daemon` — followed immediately by
`Install finished. Preparing snapshot…`. The absence is meaningful rather than
a logging gap, because install's own echoes do appear in the same log, so the
pipeline captures repository script stdout. This matches both scripts' headers:
a build preserves disk state and does not run the start phase. It does **not**
show whether start runs on an agent run, because a build is not an agent run.
That distinction is carried as this lane's single `HYPOTHESIS`.

**Terminals could not be tested at all.** `trigger-environment-build`'s
`environmentJson` override accepts only `install`, `start` and `snapshot` under
`additionalProperties: false` — a strict subset of the live environment schema.
Submitting the applied file was rejected with
`{"code":"unrecognized_keys","keys":["name","terminals"]}` and no build
started. Any claim that the validators terminal works is unproven.

A small real defect surfaced by actually running it: `pip` installs the
`jsonschema` console script to `/home/ubuntu/.local/bin`, which is not on
`PATH`. The Python import is what `start.sh` and the validators use and it
works, so nothing is broken. Recorded because it is a real warning in a real
log, and because the alternative — noticing it and not writing it down — is the
habit this operation is trying to break.

### 4. The repository `environment.json` is not this environment's configuration source

`DIRECTLY_REPRODUCED` observation resting on a `DOCUMENTED` tool contract, and
it settles the first open item in L1's `could_not_verify` table.

`environment-info` reports `environmentJsonPath: null` and `source: Team`.
`trigger-environment-build`'s contract states the `environmentJson` override
*"is not supported for repo-file managed environments … and is rejected for
them"*. This environment accepted the override and built. Therefore the
environment is **db-managed**, and the repository file is not read as its
source. That is why `name` and `install` in a schema-valid 135-byte file
produced `environmentJson: null` and the note *"environment.json was found but
contained no recognized configuration fields."*

L1 could not distinguish "the saved Team record is empty" from "the repository
file loses to it" from inside the pod. The build settles it: the saved record
is the source.

So the applied `environment.json` is correct, valid and **inert**. Applying it
changed no behaviour and reverting it would change none. Making it effective is
`FA-W2-ENV-01`.

## What was added beyond the apply, and what each traces to

Five changes. Every one traces to a named gap or a reproduced defect; nothing
was added because it seemed like good governance.

| Change | Traces to |
|---|---|
| `.cursor/mcp.json`, real and strictly parseable, `mcpServers` empty by decision | G9, and the staged file being marked DO NOT COPY |
| `"disableAllMcpServers": false` in `environment.json` | G9 — policy stated rather than silently inherited |
| `.cursor/hooks/probe_hook_firing.py` | reproduced defect: `APPLY.md`'s probe is unsafe by construction |
| `protected_path_globs` labelled advisory in `write-scope.json` | reproduced defect: no code reads that key |
| No `.cursorignore` | G9, decided against on documented grounds |

The MCP reasoning is in `W2-MCP-POLICY-DECISION-20260822-v001.json`. The short
version: `mcpServers` is empty **by decision**, because the two servers this
estate depends on are Cursor built-ins a project file cannot add,
`Cloudflare-docs` is already available at team level, the five `needsAuth`
servers cannot be authenticated from inside a pod, and the staged record's own
top candidate is self-described as *"candidate; no such server has been
evaluated or named"*. `disableAllMcpServers` is set to the permissive value
because the authority in force says unauthenticated integrations are a blocker
to remove rather than a boundary to respect — setting `true` would be a
capability regression dressed as governance. `mcpServerAllowlist` is left unset
because writing one requires `serverUrl` or `command` patterns that are not
observable from inside the pod, and an empty array is documented to be
behaviourally identical to omission — adding one would create exactly the
declared-but-unenforced key this lane just criticised.

`.cursorignore` was decided against on documented grounds: it cannot enforce
anything, because the terminal tool bypasses it by design. Using it to make a
prose prohibition into a mechanism would manufacture the same defect
deliberately. The repository holds no credential files, and blocking
`receipts/**/raw/**` would break independent acceptance, whose job is replaying
raw evidence. The one legitimate candidate is `.cursorindexingignore` over the
largest third-party captures, which keeps them readable while removing them
from search — recorded, not applied, because that path is outside this lane's
declared write scope.

## The defect in `write-scope.json` worth naming on its own

`write-scope.json` declares `protected_path_globs` listing
`workstreams/po03/**`, `state/**`, `.github/workflows/**` and `.cursor/**`.
A repository-wide search returns exactly one hit: its own definition. The guard
inspects the command string and the branch, never the staged paths.

It is a key that looks like a boundary and refuses nothing, sitting inside the
one file whose stated purpose is to be the single enforced statement of scope —
*"Do not restate a boundary in prose somewhere else"*. A reader checking
whether `.cursor/**` is protected would conclude yes.

It was labelled rather than enforced or deleted. Enforcing it would refuse
commits touching `.cursor/**` and `state/**`, which are precisely the paths
configuration and control-plane lanes legitimately write — including this one —
and an over-broad guard blocking legitimate work is the first risk `APPLY.md`
names. Deleting it would lose the record of which surfaces a reviewer should
look at. So it now says what it is.
